## 1. 项目现状与结论

当前项目目录以以下产品规划和架构决策文档为基线：

- `CanLearn_Product_Plan_v2.0.tex`
- `CanLearn_Product_Plan_v2.1.tex`
- `architecture/ADR-0001-technology-stack.md`

目前未发现应用代码、数据库脚本、部署配置或自动化测试。因此，当前项目处于**技术栈已确定、工程骨架待建立**的准备阶段，不是已经实现的软件稳定版。

V2.1 文档也明确说明：

- 技术栈已经确定，但功能范围、指标阈值和路线图仍属于规划，不代表相关功能已经上线或通过实测，见产品方案“修订摘要与证据口径”。
- 服务边界和渐进式拆分方式是已采用的工程基线，不是既有系统实现，见产品方案“微服务架构与业务编排”。
- 附录中的 RESTful API 是待实现的业务契约，不是已经交付的接口，见产品方案“关键数据与接口契约”。

因此，本方案将 V2.1 作为需求基线，但在正式研发前还需要将其转化为：

1. 可执行的产品待办清单；
2. 正式的数据模型和 API 契约；
3. 可逐项检查的验收用例；
4. 稳定版非功能指标；
5. 发布、回滚、备份和故障处理规范。

### 1.1 V2.1 相比 V2.0 的主要变化

V2.1 主要是一次外部事实和技术依赖复核，而不是大规模功能改版，主要变化包括：

- MinerU 首轮评估候选版本由 3.4.5 更新为 4.0.7；
- MinerU 集成改为 V1 HTTP API；
- 解析策略调整为 `flash`、`basic`、`standard`、`advanced` 档位；
- 增加 MinerU 3.x 到 4.0 的迁移注意事项；
- 更新结果契约、页码索引和任务恢复风险；
- 更新竞品资料与研究截止日期。

V2.1 的核心功能分层、路线图和产品主线与 V2.0 基本一致。

### 1.2 2026-09-30 技术栈决策

以下选型已从“建议/候选”升级为研发基线：

| 层次 | 已确定选型 | 主要责任 |
| --- | --- | --- |
| Web 前端 | Next.js | 学习工作台、资料阅读、练习、计划与任务状态 |
| 主业务后端 | Node.js + TypeScript + NestJS/Fastify | 模块化单体、权限、业务规则、数据写入和外部 API |
| 数据访问 | Drizzle ORM | PostgreSQL Schema、查询和迁移 |
| 工作流与 AI 工作者 | Python + Temporal | 长任务编排、模型调用、生成、校验、重试和补偿 |
| 文档解析 | MinerU 微服务 | PDF 解析，通过 V1 HTTP API 和版本化 Adapter 接入 |
| 主数据库 | PostgreSQL | 权威业务数据、关系约束、事务、版本和审计 |
| 高速数据层 | Redis | 缓存、限流、短期协调、锁和队列/任务通知 |
| 接口结构 | RESTful API + OpenAPI | 前后端及同步服务调用的版本化契约 |

详细边界记录在 `architecture/ADR-0001-technology-stack.md`。身份认证、Redis 是否需要独立队列库、对象存储、向量检索和生产部署平台仍待后续 ADR 确定，不得在实现中无记录地默认选择。

## 2. 项目内容确认

### 2.1 产品定位

CanLearn 是一个面向自主学习者的跨学科、资料驱动学习平台。其核心流程是：

> 资料导入 → 解析和知识组织 → 讲解与练习 → 学习证据 → 计划恢复

产品不是简单的 PDF 问答工具，也不是单一的 408 备考软件。408 和英语四六级是首批公共内容，但底层数据模型和主要业务流程应保持学科无关。

对应依据：

- 产品定义与主线：产品方案“项目总览”
- 用户边界与产品原则：产品方案“产品战略与目标用户”
- 核心学习闭环：产品方案“核心体验与使用场景”

### 2.2 P0/MVP 范围

V2.1 定义的首发范围包括：

- 全学科学习目标创建；
- 多目标登记、优先级和总容量基础校验；
- 私有学习空间；
- PDF 上传；
- MinerU 异步解析；
- 解析状态、质量检查和来源定位；
- 公共 408、英语四级和六级种子内容；
- 基础知识地图；
- 带来源引用的文字讲解；
- 单选、填空和短答练习；
- 作答记录和学习证据；
- 近期学习计划；
- 中断后的恢复提案；
- 计划版本确认和撤销；
- 数据导出和全链路删除。

对应依据：产品方案“产品范围与信息架构”。

### 2.3 首发不应包含的内容

以下内容应明确后置：

- 完整全学科题库；
- 复杂跨目标全局优化；
- 自动官方考试评分；
- 听力音频处理和口语训练；
- 音视频讲解；
- 机构管理端；
- 复杂知识图谱可视化；
- 大规模多集群部署；
- 未获得权利的教材、题库和解析内容；
- 无配额、无预算限制的无限生成。

对应依据：产品方案“范围分层与版本取舍”和“可以按需后移的工作”。

### 2.4 推荐的首个稳定候选范围

考虑只有四名研发人员，第一个稳定候选版本应进一步收敛为：

1. 私有 PDF 单章节学习闭环；
2. 可追溯到文档版本、页码和区域的引用；
3. 基础讲解；
4. 单选、填空、短答三种题型；
5. 作答记录和基础可信证据；
6. 简化的近期计划和恢复提案；
7. 多目标登记与总容量检查；
8. 计划确认与撤销；
9. 任务取消、数据导出和全链路删除；
10. 少量经过外部学科审校的 408/四六级种子内容。

## 3. 技术落地原则

### 3.1 不宜一开始建设大量物理微服务

V2.1 逻辑上划分了 Document、Content、Retrieval、Exercise、Explanation、Validation、Evidence、Planner 和 Workflow 等模块。但四人团队不适合一开始部署八个以上独立服务。

确定采用：

> Next.js Web + NestJS/Fastify/TypeScript 模块化主后端 + Python/Temporal 工作流 + 独立 MinerU 微服务 + PostgreSQL + Redis

具体建议：

- Next.js Web 前端独立部署，只访问 CanLearn RESTful API；
- Node.js/TypeScript 业务 API 采用 NestJS + Fastify 模块化单体，以 Drizzle ORM 访问 PostgreSQL，并维护 OpenAPI 契约；
- Python 层采用 Temporal 负责长任务编排、生成和校验工作者；
- MinerU 解析进程与 GPU 资源独立部署，由主后端通过 Adapter 接入；
- PostgreSQL 是权威业务数据源；
- Redis 只承担缓存、限流、短期协调、锁和队列/任务通知，不作为不可恢复业务事实的唯一存储；
- 讲解、练习和校验保留独立内部契约，但初期可以共用工作者部署；
- PostgreSQL 初期共用实例，但模块写入责任必须明确；
- 达到负载、权限或独立发布需求后再进行物理拆分。

这与产品方案“微服务架构与业务编排”中的渐进式拆分原则一致。

### 3.2 必须优先保证的工程属性

首版不能后补的能力包括：

- 资源和来源版本；
- 用户、租户和私有空间权限；
- 状态机和持久化任务记录；
- 幂等、重试、超时和取消；
- 晚到结果处理；
- 质量状态；
- 基础费用和资源消耗记录；
- 数据导出及删除；
- 题目、讲解、证据和计划的版本关系；
- 审计记录。

对应依据：产品方案“状态、可靠性与成本护栏”和“不能被后移的工作”。

## 4. 团队角色与责任边界

本方案使用以下代号：

- **A：高级架构师兼全栈工程师**
- **B：前后端工程师**
- **C：学员一，解析与质量方向**
- **D：学员二，体验与验收方向**

### 4.1 A：高级架构师兼全栈工程师

#### 主要职责

- 担任技术负责人和临时产品技术负责人；
- 确定系统边界、模块划分和演进路线；
- 设计核心数据模型；
- 负责权限、租户隔离和数据生命周期；
- 负责持久化工作流、状态机、幂等和补偿策略；
- 负责 Node.js 主后端与 Python 工作流之间的责任边界和数据一致性；
- 负责 Evidence、Planner 和 Plan Patch 核心规则；
- 负责删除、导出、成本账本和发布门禁；
- 审批跨模块 RFC 和重要 ADR；
- 处理高风险技术问题和严重生产事故；
- 决定是否允许发布。

#### 责任边界

- 不包办全部开发工作；
- 不长期承担所有普通任务的第一审核人；
- 自己提交的高风险功能不能自己完成全部审核和验收；
- 不能代替学科专家完成公共内容正确性签署；
- 不能以架构设计替代真实测试和用户验收。

### 4.2 B：前后端工程师

#### 主要职责

- 担任日常交付负责人；
- 负责 Next.js Web、BFF 和 Node.js/TypeScript 业务 API；
- 负责目标、学习空间、资料、练习和计划页面；
- 负责 RESTful Document API、Job API 和 MinerU Adapter 的业务集成；
- 负责 Retrieval、讲解、练习、作答等端到端链路；
- 维护正式 OpenAPI 和前后端示例；
- 建设集成测试和预发布环境；
- 负责日常构建、部署、发布和回滚执行；
- 指导两名学员完成可独立交付的子任务。

#### 责任边界

未经架构评审，不得自行改变：

- 核心状态机；
- 权限和租户模型；
- 数据所有权；
- Evidence/Planner 语义；
- 删除流程；
- 公共内容发布条件。

### 4.3 C：学员一——解析与质量方向

#### 可独立负责

- 合法测试集目录和授权元数据；
- MinerU 请求/响应夹具；
- 输出 Schema 校验；
- 0 起始和 1 起始页码转换测试；
- 文本、扫描、双栏、公式、表格和跨页样本测试；
- 引用回跳抽样检查；
- 解析失败分类；
- 重复提交、超时、取消和晚到结果测试；
- 解析质量、任务成功率和成本报表；
- 故障复现说明和运行手册。

#### 不得单独负责

- 生产数据库迁移；
- 生产密钥和供应商密钥；
- 权限与租户逻辑；
- 删除核心逻辑；
- 生产部署和回滚；
- 公共内容发布；
- 解析版本和模型版本的最终选型。

### 4.4 D：学员二——体验与验收方向

#### 可独立负责

- 排队、运行中、部分可用、失败和取消等状态组件；
- PDF 引用跳转和高亮体验；
- 解析纠错表单；
- 配额和预计消耗提示；
- 基础页面和叶子组件；
- 事件埋点校验；
- 桌面端和移动端 E2E；
- 可访问性检查；
- UAT 验收脚本；
- 发布前和发布后的冒烟测试；
- 用户测试记录和问题归档。

#### 不得单独负责

- 判分规则；
- 掌握度计算；
- Evidence 写入规则；
- Planner 和 Plan Patch；
- 计费与额度扣减；
- 权限策略；
- 数据库迁移；
- 公共题目和讲解发布。

### 4.5 必须补充的外部责任

四人团队中没有完整覆盖以下专业能力：

1. 408/四六级学科审校；
2. 内容版权、许可证、隐私和合规审批。

因此必须指定兼职、合作或外部责任人。没有对应审批时：

- 私有资料功能可以继续研发和受控测试；
- 公共内容必须保持 `Blocked`；
- 不得由学员或开发人员代替专业签署。

## 6. Git 提交之外的协作机制

Git 只能保存变更，不能替代需求管理、设计决策、验收和发布治理。团队必须建立以下协作物。

### 6.1 统一任务卡

每个任务必须包含：

- 工作项编号；
- 用户场景；
- 业务目标；
- 本次范围；
- 明确非范围；
- 前置依赖；
- 输入和输出；
- API 或事件影响；
- 权限和数据影响；
- 正常验收场景；
- 失败、超时、取消、重试和删除场景；
- 埋点及监控指标；
- 开发负责人；
- 审核人；
- 验收人；
- 回滚方案；
- 相关 V2.1 章节或行号。

任务标题应描述用户价值，例如：

- 推荐：`用户上传 PDF 后可以看到逐页解析状态`
- 不推荐：`完成 MinerU 接口`

### 6.2 RFC

以下变化必须先写 RFC：

- 跨模块数据流；
- 数据所有权变化；
- 权限和租户策略；
- 文档删除；
- 工作流状态机；
- Evidence 和 Planner 规则；
- 新的外部模型或解析供应商；
- 重大依赖升级；
- 新公共内容发布流程。

RFC 至少包括：背景、目标、非目标、方案、备选方案、数据生命周期、失败处理、安全影响、成本影响、迁移和回滚。

### 6.3 ADR

已经确定的重要决策写入 ADR，包括：

- Next.js、Node.js/TypeScript、Python、MinerU、PostgreSQL、Redis 与 RESTful API 基础技术栈；
- 为什么采用模块化单体而不是立即拆成大量微服务；
- MinerU 固定版本和输出适配方案；
- 业务任务状态机；
- 数据库模块写入权限；
- 向量索引和关系数据库的职责；
- 内容版本和引用模型；
- 删除及晚到结果处理方式。

ADR 记录的是已经作出的决策，不应被聊天记录替代。

### 6.4 正式接口与事件契约

同步业务接口采用 RESTful API，并使用 OpenAPI 作为前后端和服务调用的唯一同步接口依据；异步工作流继续使用版本化事件 Schema。契约必须覆盖：

- 身份和资源权限；
- 幂等键；
- 业务版本；
- 工作流和任务标识；
- 状态和阶段进度；
- 部分成功；
- 错误码；
- 配额不足；
- 版本冲突；
- 取消；
- 删除；
- 可重试和不可重试错误。

前端不得直接连接 MinerU，只能连接 CanLearn 业务 API。
前端同样不得直接连接 PostgreSQL 或 Redis。长耗时接口返回 `202 Accepted` 和任务标识，不保持同步请求等待解析或生成完成。

### 6.5 测试证据包

每项进入验收的功能应附：

- 自动化测试结果；
- 测试环境和版本；
- 测试数据说明；
- E2E 截图或录屏；
- `trace_id`、`workflow_id` 或 `task_id`；
- 已知限制；
- 回归范围；
- 未解决问题。

### 6.6 运行手册

至少包含：

- 服务启动和停止；
- 队列积压处理；
- MinerU 失败重跑；
- 任务取消；
- 晚到结果处理；
- 索引重建；
- 数据删除；
- 数据恢复；
- 版本回滚；
- 模型或供应商异常降级；
- 成本异常处理；
- 安全事故上报。

### 6.7 发布清单和事故复盘

每次发布都应有：

- 版本范围；
- 数据库迁移；
- 功能开关；
- 监控和告警；
- 回滚步骤；
- 许可证和模型快照；
- 已知问题；
- 发布负责人；
- 发布后观察结果。

发生严重事故后应在两个工作日内完成复盘，记录事实、影响、根因、修复项、负责人和防止复发的验证方式。

## 7. 工作流与看板

建议使用以下看板状态：

> Inbox → Refinement → Ready → In Dev → Review → Staging → Acceptance → Done

另设：

- `Blocked`：存在外部依赖、审批或技术阻塞；
- `Rejected`：验收失败，需要重新进入开发；
- `Dropped`：明确取消并记录原因。

### 7.1 状态进入条件

#### Ready

必须已经具备：

- 清楚的范围和非范围；
- 输入、输出和样例；
- 验收条件；
- 依赖已满足；
- 权限和数据影响已说明；
- 任务大小不超过预计两个工作日，或已拆分。

#### Review

必须具备：

- 实现完成；
- 本地测试通过；
- 文档和契约同步；
- 无明文密钥；
- 开发者完成自检。

#### Acceptance

必须具备：

- 已部署至预发布环境；
- 测试证据包齐全；
- 独立验收人可以复现；
- 监控和错误行为可观察。

#### Done

必须具备：

- 验收通过；
- 相关文档更新；
- 无阻断问题；
- 功能开关和回滚方案明确；
- 如已发布，发布后冒烟测试通过。

### 7.2 WIP 限制

- 每人同时最多一个主要开发任务；
- 团队同时处于 Review 的任务不超过两个；
- 学员任务以 0.5～2 个工作日为宜；
- 阻塞超过一个工作日，由 A 负责推动解决；
- 不允许因“等审核”而同时开启多个半成品任务；
- 代码合并不等于任务完成。

---

## 8. 审核机制

### 8.1 普通改动

- 至少由 A 或 B 中一人审核；
- 学员不得自审、自验收；
- 必须附自动化测试或明确可复现步骤；
- API、文档和测试必须随实现同步更新。

### 8.2 高风险改动

以下内容必须由 A、B 双人参与，其中至少一人为非作者，并附独立测试证据：

- 身份、权限和租户隔离；
- 数据库迁移；
- 数据删除和导出；
- 计费、额度和成本账本；
- 判分和学习证据；
- Planner 和 Plan Patch；
- 工作流状态机；
- 幂等、重试和补偿；
- 公共内容发布；
- 生产依赖升级；
- 模型和供应商切换。

### 8.3 直接阻断发布的问题

以下问题不允许带病发布：

- 越权读取；
- 私有资料进入其他用户检索；
- 删除后内容仍可访问或重新被索引；
- 晚到结果使已删除内容重新出现；
- 重复事件导致重复计分或重复扣费；
- 已完成任务被无授权改写；
- 引用无法定位到正确来源；
- 未通过质量门禁的内容进入正式诊断；
- 未经权利和学科审核的内容进入公共库；
- 生产密钥泄漏；
- 无法回滚的高风险迁移。

对应依据：产品方案“首轮工程服务目标”和“内容、数据与 AI 治理”。

### 8.4 内容审核

公共题目和讲解必须同时通过：

1. 技术结构和可用性检查；
2. 来源和内容权利检查；
3. 学科正确性审校；
4. 发布记录签署。

多个模型输出一致、开发者认为正确或自动评分较高，都不能替代学科审校。

## 10. 研发和验收流程

### 10.1 需求阶段

每张卡必须说明：

- 用户为何需要；
- 做到什么程度算完成；
- 哪些内容本次不做；
- 失败时用户看到什么；
- 如何采集验证数据；
- 如何判断是否值得继续投入。

### 10.2 三方澄清

开发前由三类人员共同确认：

- 需求/技术负责人；
- 实现人员；
- 测试或验收人员。

澄清重点：

- 依赖是否可用；
- 测试资料是否合法；
- 接口是否明确；
- 权限和删除是否考虑；
- 验收是否可执行；
- 任务是否需要继续拆分。

### 10.3 设计阶段

跨模块功能必须覆盖：

- 数据流；
- 状态机；
- 权限；
- 幂等；
- 重试和超时；
- 取消和删除；
- 成本和配额；
- 监控；
- 迁移；
- 回滚；
- 安全威胁。

### 10.4 API 优先

先定义请求、响应、错误码和状态样例，再分别实现前端与后端。API 评审通过前，前端可以使用固定 Mock，但不得根据临时后端返回自由推断正式契约。

### 10.5 测试顺序

1. 单元测试；
2. Schema 和契约测试；
3. MinerU Adapter 集成测试；
4. 数据库和队列集成测试；
5. 权限测试；
6. 故障注入；
7. 端到端用户路径；
8. 固定基准集；
9. UAT；
10. 发布冒烟和发布后观察。

必须测试：

- 重复提交；
- 网络超时；
- 工作者重启；
- 部分页面失败；
- 用户取消；
- 用户删除；
- 晚到结果；
- 资料版本变化；
- 计划版本冲突；
- 费用超限；
- 外部服务不可用。

### 10.6 验收阶段

- C、D 在预发布环境按照任务卡独立执行；
- B 验收完整用户路径；
- A 验收架构、安全和业务硬约束；
- 结果以测试报告、截图、日志标识和指标查询留证；
- 不接受“代码已经合并”作为验收结果。

### 10.7 发布阶段

采用以下顺序：

> 功能开关关闭部署 → 内部烟测 → 小范围打开 → 受邀用户灰度 → 观察指标 → 扩大范围

发布包必须包含：

- 数据库迁移；
- 回滚方式；
- 监控和告警；
- 已知限制；
- 模型、提示模板和依赖版本；
- 许可证快照；
- 功能开关；
- 值守责任人。

### 10.8 发布后

发布后 24 小时检查：

- 权限错误；
- 异常率；
- 队列积压；
- 任务延迟；
- 模型和 GPU 成本；
- 删除任务；
- 死信任务；
- 用户投诉。

发布后一周复盘：

- 上传后首个可用章节率；
- 首个 VLU 完成率；
- 引用打开和纠错；
- 计划接受、拒绝和撤销；
- 用户留存；
- 每个有效学习单元的成本。

## 11. 会议和沟通节奏

### 11.1 每日异步更新

每人每天更新三项：

1. 昨日完成的可验证结果；
2. 今日唯一主要目标；
3. 阻塞和所需帮助。

不要求为了会议重复口头汇报看板已有信息。

### 11.2 周一：规划和澄清，45 分钟

内容：

- 检查上周未完成任务；
- 选择本周端到端增量；
- 拆分工作项；
- 确认验收人；
- 检查外部依赖和审批；
- 控制 WIP。

### 11.3 周三：架构/API/风险评审，30 分钟

只讨论：

- RFC 和 ADR；
- API 或 Schema 变化；
- 权限、数据和成本风险；
- 阻塞超过一天的问题；
- 是否需要缩小范围。

### 11.4 周五：演示、验收和复盘

- 45 分钟真实环境演示和验收；
- 30 分钟复盘。

演示必须使用真实流程和合法测试数据，不能只展示静态页面或单独接口响应。

### 11.5 学员 Office Hour

每周安排两次、每次 30 分钟的集中答疑。其他时间学员先按照任务卡、契约和运行手册自行排查，减少 A 成为即时答疑瓶颈。

## 12. 质量门禁

### G0：需求门

必须具备：

- 合法测试样本；
- 用户场景；
- 范围和非范围；
- 验收标准；
- 权限和权利说明；
- 指标和埋点。

### G1：设计门

必须完成评审：

- 模块责任；
- 数据所有权；
- 状态机；
- 权限矩阵；
- 失败、取消和删除；
- 成本预算；
- 迁移和回滚；
- 威胁模型。

### G2：实现门

必须通过：

- 格式和静态检查；
- 类型检查；
- 单元测试；
- 依赖漏洞检查；
- 密钥检查；
- 数据迁移检查；
- 功能开关检查。

### G3：契约和可靠性门

必须验证：

- API 契约；
- 事件契约；
- MinerU Adapter 契约；
- 幂等；
- 重试和超时；
- 版本冲突；
- 取消；
- 删除；
- 晚到结果；
- 部分成功；
- 故障恢复。

### G4：内容质量门

V2.1 建议的首轮解析指标包括：

- 每个请求页都有状态记录：100%；
- 清晰文本字符编辑错误率：不高于 1%；
- 清晰扫描字符编辑错误率：不高于 5%；
- 阅读顺序一致率：不低于 98%；
- 公式合格率：不低于 95%；
- 表格合格率：不低于 90%；
- 来源回跳正确率：不低于 99%；
- 题目结构化完整率：不低于 95%；
- 可观察失败率：100%。

对应依据：产品方案“解析质量门禁与基准集”。

这些指标必须按文档类型和样本量报告，不能通过排除困难资料美化平均结果。

题目还应通过：

1. 结构与可答性；
2. 答案核验；
3. 依据和引用；
4. 干扰项和歧义；
5. 覆盖与重复；
6. 权利和安全。

对应依据：产品方案“六道质量门禁”和“题目生命周期与用途隔离”。

### G5：体验门

必须检查：

- 桌面和移动端核心路径；
- 键盘操作和基础可访问性；
- 排队、部分可用和失败状态；
- 取消和重试；
- 错误提示；
- 引用跳转；
- 删除状态；
- 用户可理解的配额和成本。

V2.1 给出的首轮候选体验目标为：

- 20 页以内普通资料，首个可用章节 P95 不超过 180 秒；
- 已有可用证据的文字讲解 P95 不超过 30 秒；
- 十题生成和校验 P95 不超过 120 秒。

对应依据：产品方案“首轮工程服务目标”。这些是候选目标，不是当前已经达到的承诺。

### G6：发布门

必须满足：

- 阻断缺陷为零；
- 依赖、镜像、模型和提示模板版本固定；
- 许可证快照完成；
- 外部内容审批完成；
- 备份恢复已演练；
- 回滚已演练；
- 删除已演练；
- 监控和告警已经启用；
- 发布和值守责任人明确。

## 13. 建议阶段排期

### R0：定义与基准，第 1～2 周

#### A

- 确定模块边界；
- 建立核心 ADR；
- 定义权限、数据生命周期和删除模型；
- 定义工作流状态；
- 补充稳定版指标；
- 明确发布阻断条件。

#### B

- 建立 Next.js 前端项目骨架；
- 建立 Node.js/TypeScript 模块化主后端和 RESTful API 骨架；
- 建立 PostgreSQL 迁移和 Redis 基础连接；
- 建立开发和预发布环境；
- 完成 OpenAPI 初稿；
- 实现基础 Job 状态展示。

#### C

- 建立 Python 工作流/生成校验工作者骨架；
- 建立约 12 份、120 页的首轮烟测集；
- 固定测试资料类型和授权记录；
- 建立 MinerU 请求/响应夹具；
- 编写解析 Schema 和页码契约测试。

#### D

- 制作主流程可点击原型；
- 编写首批 UAT；
- 定义页面状态和错误体验；
- 准备用户测试脚本。

#### 退出条件

- 合法样本可用；
- Next.js、Node.js/TypeScript、Python、PostgreSQL、Redis 和 MinerU 的最小开发链路可运行；
- MinerU 和模型版本固定；
- 最小链路风险可测；
- API、权限和状态机完成第一次评审；
- OpenAPI 与异步事件 Schema 完成第一次契约测试；
- 核心任务可以拆成两天内的工作项。

### R1A：资料闭环，第 3～4 周

交付：

> 上传 → 任务 → MinerU 解析 → 标准化 → 质量状态 → 引用阅读 → 指定页纠错

重点测试：重复提交、部分页失败、取消、重启、晚到结果、版本变化和删除。

### R1B：学习闭环，第 5～6 周

交付：

> 证据检索 → 讲解 → 练习 → 校验 → 作答 → Evidence → 近期计划 → 恢复提案 → 确认/撤销

种子内容只交付少量、经过外部学科审校的单元，不追求题目数量。

### R2：受邀 Beta，第 7～10 周

交付：

- 解析纠错传播；
- 题目审校台；
- 队列、质量和成本看板；
- 多目标总容量；
- 用户反馈和申诉；
- 固定回归集扩展到约 60 份、600 页；
- 小范围受邀用户观察。

只有质量、安全和服务稳定性达到预设线后才扩大用户规模。

### R3A：稳定性验收，第 11～12 周

重点：

- 性能压测；
- 错误率和可用性；
- 备份恢复；
- 回滚演练；
- 删除演练；
- 权限专项测试；
- 成本上限；
- 运行手册；
- 值守和事故响应。

### R3B：付费和权益实验，第 13～14 周

只有 R3A 通过后才进入：

- 权益和配额实验；
- 真实支付；
- 退款流程；
- 重度用户成本观察；
- 写作和翻译反馈的小范围试用。

### 后置阶段

音频、听力、口语、音视频讲解、更多公共包和机构端全部后置。每项新能力都必须先具备合法来源、审校能力、专项基准和成本边界。

## 14. 稳定版需要补充的正式定义

## 15. 主要风险与应对

### 15.1 范围过大

**风险：**四人团队同时做解析、生成、题库、计划、内容、支付和多模态，容易形成大量半成品。

**应对：**优先交付私有 PDF 单章节闭环；用端到端薄切片代替按技术层横向铺开；P1/P2 严格后置。

### 15.2 A 成为团队瓶颈

**风险：**所有设计、代码和问题都等待 A，导致团队停滞。

**应对：**

- 使用契约和 ADR 固化决策；
- B 负责日常交付；
- 固定架构评审和 Office Hour；
- A 只重点审核跨模块和高风险事项；
- 学员任务给出明确样例和验收标准。

### 15.3 学员任务失控

**风险：**任务太大或涉及核心业务，出现返工和安全问题。

**应对：**

- 每项 0.5～2 天；
- 采用低权限开发凭据；
- 只使用合成或合法测试资料；
- 功能开关默认关闭；
- 开始前短时间结对；
- 完成后由经验成员审核和独立验收。

### 15.4 MinerU 上游任务不可恢复

**风险：**上游重启后任务状态丢失，导致平台无法判断真实处理状态。

**应对：**

- 固定 MinerU 4.0.7 候选版本、依赖和镜像摘要；
- 通过 Adapter 隔离；
- CanLearn 持久化自己的任务状态、输入快照和上游映射；
- 测试重启、重试、取消和晚到结果。

对应依据：产品方案“服务集成：评估 4.0.7 与 3.x 迁移”和“必须澄清的职责边界”。

### 15.5 学科正确性和版权能力不足

**风险：**生成内容错误，或将无权资料发布到公共库。

**应对：**

- 公共内容设置外部审批硬闸门；
- 建立来源和权利台账；
- 内容按候选、基础校验、已审校和已校准分级；
- 没有审校资源时只做私有资料流程。

### 15.6 模型幻觉和错误诊断

**风险：**错误讲解、错误题目或无效证据影响用户计划。

**应对：**

- 使用带版本的来源证据包；
- 独立求解和 Validation；
- 限制自动修复次数；
- 低质量结果不进入正式证据；
- 题目纠错后撤销错误计分并重算；
- 模型不得直接更新掌握度和计划。

### 15.7 隐私、越权和删除失效

**风险：**私有内容泄漏、缓存跨空间复用、删除后数据重新出现。

**应对：**

- 所有资产继承权限域；
- 检索、展示、导出时重新鉴权；
- 删除先撤销访问，再清理资产；
- 每一步写入前检查删除标记；
- 定期演练晚到结果和索引删除。

### 15.8 成本和算力波动

**风险：**解析和生成成本失控，或者服务为降低成本偷偷降低质量。

**应对：**

- 队列隔离；
- 分步骤记账；
- 开始前预估；
- 任务预算上限；
- 修复次数上限；
- 优先复用已审校内容；
- 不静默切换到未审核的外部服务；
- 分文档类型报告质量和成本。

## 16. 最终建议

对于这一四人团队，最有效的组织方式不是把工作简单分成“前端、后端、AI、测试”四块，而是：

- 以端到端用户路径为每个迭代的交付单位；
- A 控制架构、权限、数据、状态机、Evidence/Planner 和发布风险；
- B 负责日常集成、前后端和完整功能落地；
- C 专注解析基准、契约、可靠性和质量数据；
- D 专注用户状态、引用体验、E2E 和独立验收；
- 公共内容由外部学科与权利责任人审批；
- 用任务卡、RFC、ADR、OpenAPI、测试证据包、运行手册和发布清单补足 Git 之外的协作；
- 以质量门禁和真实验收决定阶段退出，而不是按日期自动宣布稳定。

在此模式下，两名学员可以交付真实、有边界、可验证的工作，同时不会让权限、删除、判分、计划和公共内容等高风险能力失控。高级架构师也能够从“所有事情亲自做”转向“控制关键边界和风险”，使四人团队具备持续交付能力。
