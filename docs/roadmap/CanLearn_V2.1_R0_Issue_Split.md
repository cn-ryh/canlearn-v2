## 录入及关闭规则

- `CL-001a` 等是项目追踪 ID，GitHub 分配的编号见下表。本次按用户请求一次性创建了 14 个父 Issue 和 40 个原生子 Issue；父子关联及依赖链接已写入 GitHub 描述，但**未自动指派成员或宣称任务已完成**。不要把同一工作同时当作父卡和子卡各做一次。R1A 及后续仍按容量滚动创建。
- **父卡只做范围与综合验收，不是下游子卡的依赖门槛。** 子卡的“依赖”是开始所需的具体输入；写作 `CL-xxx(a/b)` 表示对应子卡先完成，不意味着必须等该父卡全部关闭。除标出的依赖外可并行；有外部审批或样本未到时记录 Blocked 和负责人，不自行宣称通过。
- 标签继承父卡的 `phase:R0`/`priority`/`area`；研究、决策、测试额外按 `kind:research|decision|test|docs` 标记。角色：A 架构/高风险审核，B 前后端，C 解析与质量，D 体验与验收。建议主责不是已指派；每卡开工前填写实际负责人、非作者审核人、验收人。合规/权利、教学审校须指定**外部真实责任人**，不能以开发自签代替。
- R0 大部分是需求、评测、契约或最小纵向烟测，不要求在此阶段实现完整生产功能。文档/研究卡的 DoD 是**可检验的工件＋评审结论/未决项**，无代码不强行附 PR 或编造 `pnpm verify` 结果；改动代码/契约/配置的卡须附 PR、`pnpm verify` 结果和失败/回滚说明。测试样本须有可证明的使用权；私有/受限 PDF 及访问凭证不提交仓库。具体取舍以总待办的通用 DoD/G0/G1 为准。
- 小卡以**一个主产出、一个可独立验收点**为原则。若估计超过约 2 个有效工作日、不同人需分别交付，继续拆；若只是同一验收中的建表/画按钮等步骤，保留 Issue 内任务列表。不要用“完成某文件”替代用户或系统行为验收。
