## 0. 如何使用这份清单

- `CL-xxx` 是项目追踪 ID，而非 GitHub 自动分配的 `#编号`。R0 的 14 个父 Issue、40 个原生子 Issue 已创建，编号及依赖见 [R0 拆分与对照表](CanLearn_V2.1_R0_Issue_Split.md#github-issue-编号对照已创建)；R1A 及以后尚未创建。后续仍按阶段评审和团队容量滚动创建，不把所有规划卡片一次性发布为无负责人的 Issue。
- 推荐标签：`priority:P0|P1|P2`、`phase:R0|R1A|R1B|R2|R3A|R3B|later`、`area:product|web|api|workflow|content|platform|security|quality|ops`、`kind:feature|research|decision|test|docs`；状态用看板而非重复标签。P0 是首版/放行硬约束，不表示本周就能做完。
- 角色沿用四人协作方案：**A** 架构/高风险审核，**B** 前后端，**C** 解析与质量，**D** 体验与验收。主责只是初始建议；需指定实际负责人、非作者审核人及验收人。外部学科审校与权利审核**不可由开发者默认代签**。
- 各卡的“源”引用 V2.1 产品方案的**章节名**；定位时可用文末索引。依赖为 `finish-to-start` 的主依赖，未列出的常规契约/权限/测试要求仍受全局 DoD 约束。阶段只表示目标排序，不得因日历到了就绕过闸门。完成已有骨架不等于完成卡片的验收：当前仓库只有首页、健康接口、基础 jobs 表、Temporal 健康烟测、极小 OpenAPI 和 3 项单测；应用功能未交付。
- 本清单按可验收的纵向切片编写；估时/容量**不能从规划直接推算**。R0 的可执行拆分与具体依赖见 [R0 Issue 拆分](CanLearn_V2.1_R0_Issue_Split.md)；其余阶段在前置验证完成后滚动拆分。规划时把预计超过 2 个工作日的卡再拆成同一 Issue 下的子任务或独立子 Issue（先建立失败测试，再最小实现，再验收），但保留原卡作为验收父项。仅把设计稿、数据表或模型输出单独合并，不构成端到端完成。

### 通用 Issue 模板与完成定义（所有卡适用）

创建 Issue 时保留卡片自带的“交付/验收”，并补齐：使用场景与用户价值、明确非范围、输入输出及合同变化、权限和权利影响、失败/超时/取消/删除（适用则填）、依赖、实际负责人/审核/验收人、度量、回滚方式和 V2.1 来源。就绪需符合 G0/G1；关闭前附 PR、`pnpm verify` 结果、相关集成/E2E/安全测试证据、测试数据合法性、API/事件/迁移同步记录、截图或任务追踪号、已知限制与回滚方式。不适用项须说明原因，而不是空白。

**横向不变式（每项功能的验收都应复查）：** 服务端鉴权和资源权限（不能信任前端传来的空间/租户 ID）；私有资源不因缓存、检索或引用关联而跨域泄露；长任务 202 + 状态查询；重试/重放不重复发布、计分或扣额；取消/删除后晚到结果不能复活；版本冲突不能覆盖新版本；生成内容必须显示校验级别、来源或“无来源补充”，未经验证不参与强诊断；已完成任务与真实作答不能被计划修改或撤销抹掉。CI 通过不替代合法数据、真人验收、内容审校和恢复演练。
