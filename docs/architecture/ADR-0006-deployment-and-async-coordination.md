服务隔离与权威写入边界继续有效，不构成多地域主库/主动-主动架构或正式生产高可用验收。

### 公网 TCP 与服务认证方案

UDP 被封，不采用原建议的原生 WireGuard。推荐南京运行 CPU worker 与 Temporal，
宁波只部署 MinerU 及受限 HTTPS/mTLS 反向代理，公网 TCP 443 作为服务调用入口。
worker 经此入口提交/查询解析任务并领取临时结果，再由 API 复查权限/版本/删除和质量后接纳。
用户已明确按此服务位置安排推进；南京 4 核 8G 的容量未验证，不能因此推定所有服务可稳定同机。

公网解析入口同时检查固定来源 IP 和客户端证书，允许列表只开放批准的解析/状态/结果路径，
不公开管理端点；MinerU 本身只绑定回环或隔离容器网络。API 的逐任务资源授权和删除门禁
不能由 mTLS 证书代替。校验服务器证书链、域名/SAN 和有效期，不设置跳过证书验证。
代理限制请求大小、速率、在途任务、超时和响应体，配合允许目的地检查防止任意 URL 下载/重定向外发。
证书按服务独立签发，记录轮换、到期告警和吊销/移除信任的路径；私钥及密码不入仓库。

南京的 PostgreSQL、Redis、Temporal 及其 UI 保持私有访问，不因 GPU 异地部署开放其公网端口。
若选择 CPU worker 也在宁波，另行设计 Temporal gRPC 的 TLS/mTLS、命名空间/服务权限与网络策略，
不能仅套用 HTTP 代理模板。断链后有界重试与对账，未知任务不无条件重新创建，删除/取消仍阻断结果接纳。

本地合成证书验证已覆盖无客户端证书、不受信任证书、正确证书及错误服务器主机名；
没有连接南京/宁波实际服务器、配置防火墙或签发生产证书，见 [验证记录](CL-005/validation-record.md)。

PostgreSQL 保持业务事实源。Temporal 负责持久工作流、步骤重试和恢复；
Redis 用于可重建缓存、限流和短期协调，暂不新增 BullMQ/Celery 等独立业务队列。
业务事件/Outbox 和消费去重由 CL-008 定稿，Temporal 不自动替代业务原子发布、费用对账或取消/删除门禁。
Redis 锁不能替代数据库中的权威状态/版本条件。
解析、生成、校验可用独立 Temporal task queue 与活动并发限制，按实测需求拆 worker。
供应商自己的解析队列不成为 CanLearn 任务事实源，也不赋予下游结果发布资格。

4070 资源先保证 MinerU 候选评测与受限排队；embedding/本地生成若共机须给出显存、
吞吐与竞争证据，限并发并保护取消/超时，不用 GPU 名称推定模型可装载或达到 P95 目标。

2026-10-12 [CL-005b补测](CL-005/retrieval/extended-evaluation.md)：MinerU4.0.7 Basic/Torch
对300页全页解析约101–108秒；BGE查询在解析10秒后到达的串行观察等待98.3秒。
短查询突发并发未观察到OOM，整卡采样峰值由3503上升到5884 MiB，但只有Basic/简单合成资料证据。
内部建议解析与文档embedding进入同一受限GPU执行器，每次一个重任务；分开task queue或
各worker并发1本身不能实现跨worker互斥。实时查询单列有界队列/截止与资源预算，
优先继续验证相同BGE模型的CPU查询（宁波四线程中位约105ms，尚非南京容量验证），
也可进一步验证批准档位的GPU短查询余量；不自动把E5向量用于BGE索引或改为外部服务。
串行计算不等于常驻模型会释放显存，生产接入需验证驻留/卸载和取消后的资源回收。
资源接纳不得停止既有GPU服务；调度实现与API权限/取消/删除/结果接纳仍由后续卡完成。

初始内部调度建议：共享执行器同时最多1个解析/文档embedding重任务，文档embedding批量4；
全局等待重任务最多10个、每账户最多2个，超出返回可理解的配额/忙状态，而非新增无限队列。
实时查询优先评估同BGE CPU路径，建议截止2秒/等待最多20个，超限或超时返回忙/待处理；
这些数值是待CL-013负载验证的初始配置提案，不是实测并发承诺。解析超时按档位/页数定，
现有600秒只对应300页Basic实验，不把300页变成已冻结上传限制。
执行器进程退出/取消必须确认实际资源回收后再准入下一重任务；worker重启或锁租约到期
本身不证明GPU任务已退出。中央执行器保管实际进程与准入代，权威Job/预算仍在南京API。
查询不能因重任务互斥就等待约98秒而不告知超时；查询与文档吞吐分别记录。

## 开发、验证与生产的区别

现有 Compose 使用 Temporal auto-setup、开发数据库默认配置及 loopback 端口，适合开发基线。
验证环境需单独固定配置、服务身份、访问隔离、TLS、备份与恢复流程；生产需评估数据层可用性和真正的恢复能力。
ADR-0002 中生产数据库优先同地域多可用区托管的原则保持；复用单节点的提案只针对早期验证，
预算不足时限制试验范围，不将其写成已获批准的正式生产拓扑。
部署厂商、地域、资源配额和正式生产 RPO/RTO 尚未决定，最终结论需能力与费用证据。

业务 DB 与 Temporal 存储分账号/权限域；即使早期共用实例，也不共享业务写入角色。
Secrets 按服务最小范围加载和轮换，环境配置不入 Git；服务出网按批准供应商限制。
日志、错误和工作流 history/activity/heartbeat/属性只持久保存资源引用、版本和最小状态，
引用本身也要受控；运行时临时内容通过受限访问获取，不将原文/访问凭据写入历史。
Temporal 的历史大小限额不提供数据清理语义，Q09 还需决定实际历史/可见性/归档副本留存与清除能力。

## 恢复、回滚与验证

备份覆盖业务 DB、对象版本、Temporal、必要配置及删除台账；Redis AOF 若持久化内容也纳入治理。
明确恢复点、到期清除、责任人和成本，最新删除记录必须独立于旧恢复点可取得；
先隔离恢复、应用删除记录和验证不可读，再开放。索引按批准资源重建，Redis 丢失不丢业务事实。
缺最新删除记录或外部副本状态未知时不能宣称全部清除/恢复安全。

发布先验证后灰度，按服务回滚镜像与配置，数据库采用兼容迁移并验证回滚前提；
不自动降级 schema 或回滚删除状态。长运行 workflow 升级需核验历史重放兼容与 worker 版本策略，
不能简单回滚 Python 镜像就保证在途 workflow 可恢复。任务未知消耗保留待对账，不无限重跑付费步骤。

后续验证包括网络/权限、worker 重启、任务重放、Redis 丢失、DB 故障、GPU 饱和、部署回滚与隔离恢复。
当前没有执行这些测试。A 管理配置/密钥/恢复与放行，B 执行部署/回滚及非作者复核，C 留证，D 核验用户状态。
