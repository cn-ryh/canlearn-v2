# CL-005d · 内部试点故障、调度与恢复合同

2026-10-16 · #29评审修订；用户随后确认独立评审通过并授权关闭，内部部署决策已验收；不是已部署控制或已达成的RPO/RTO。
范围仍为南京业务面、宁波受限 GPU、10 人以内内部试点，不提前要求完整生产高可用。

## 进程隔离不等于故障隔离

当前 Compose 的业务 DB 与 Temporal 使用不同数据库和账号，但共用 PostgreSQL 实例及 `postgres-data` 卷。
实例故障、磁盘耗尽、I/O 饱和、宿主机故障会同时影响业务事实与工作流；分账号只提供权限边界。
原始实例/卷同时损坏时，不能依靠 Temporal history 自动找回业务事实。Redis 丢失只允许重建可重建状态。

内部试点拟接受此单点，条件是合成/试点范围受控、独立备份/删除台账可用且停止写入/恢复流程获批。
容量不足时首先暂停新重任务、降低可重建后台工作负载；优先将 **Temporal 存储迁移到独立实例/卷**，
保留南京业务 PostgreSQL 作为权威事实源，不把业务库迁到宁波 GPU。仅拆到同宿主机新卷不解决宿主机单点，
若宿主机 CPU/内存仍不足，应迁移 Temporal 服务/存储到另一个获准同地域资源或缩小试点，不能无限加队列。
迁移前 B 保留工作流/业务 ID 对账和独立备份，C 验证 replay/暂停恢复，A 决定预算与是否放行。

观测业务/Temporal DB 的磁盘、I/O等待、连接与慢查询及宿主机内存/CPU，区分二者负载来源。
候选停止新任务阈值：数据盘使用达80%、主机可用内存连续5分钟低于1GiB、或业务/Temporal持续连接失败。
这些是保守初值，A/B 必须结合南京4核8G混合负载复核；无监控或阈值未知不开放试点，不能写成实测容量。

## 唯一 GPU 准入与未知执行占用

主 API 的持久 ResourceAdmission 是解析/文档 embedding 重任务的唯一准入点；按设备 ID 维护权威 slot、
队列和递增 fencing epoch，写入与业务 Job/预算同事务。宁波仅一个受限执行器消费获准请求、管理自有实际进程，
不另造第二业务库或独立消息队列；Temporal 排队和 worker 并发限制不能绕过该准入。
既有 CL-010 独立原件探针是工程验证，不是这一全局资源调度已实现的证据。

候选限额：每设备同时1个解析/文档 embedding 重任务；FIFO等待最多10个、每账户等待最多2个；
活动和 unknown slot 另外计入在途，unknown 不让出这个唯一重任务槽。新重任务超过等待上限时明确拒绝，
由 API 按请求键去重，不在 Redis 创建无界第二队列。实时检索优先独立有界 CPU 路径，不挤入重任务 FIFO。

执行器持久记录 admission_id、设备、epoch、上游 job/受控进程引用及状态；本地操作记录不是业务事实替代。
同一 admission 的重放只能返回/查询已有执行，不重新启动。请求前先写 create_pending；发送后响应丢失则 unknown。
worker SIGKILL、heartbeat超时、租约到期、逻辑 CANCELLED、上游索引404、执行器进程重启都不等于GPU已停止。
上述任一状态未知时保留 slot 并阻断下一重任务，不能自动发新 epoch 来“抢回”仍可能运行的设备。

B/C 核对同一 admission 的上游记录、受控 PID/容器及设备状态，取得本次计算结束/自有进程确已退出的证据后，
API 才能标 released 并推进下一任务。只看到空闲显存/利用率为0不充分；无法核实时保持隔离并告知队列阻塞。
只清理本次登记的自有进程组，不能全机 pkill 或停止其他 GPU 服务。取消先阻断发布，再等待物理停止确认；
资源释放不返还已确认费用，不清除未知费用预留。真实并发、执行器重启和未知创建负例由 CL-114/115 接续。

## 内部试点恢复目标（提案，未达成）

| 数据/能力 | 候选目标与位置 | 操作者及放行要求 |
| --- | --- | --- |
| 业务事实、Temporal持久化 | RPO≤24小时；至少每24小时取得可恢复备份，超过24小时无成功备份暂停新写入/准入 | B备份/恢复，C复核，A处理损失并授权恢复 |
| 元数据与原件/正式产物版本 | 备份业务引用与对象版本清单并核哈希；不能只恢复SQL后假定对象还在，原件缺失标 unavailable | B恢复，C核完整性；缺失/孤立对象禁止发布，不将对象版本控制等同独立备份 |
| 最新删除/撤销台账 | 对已确认成功的删除阻断目标RPO=0；权威最新水位及完整条目保存在旧DB恢复点之外的独立持久副本 | A审批策略，B实现持久复制/对账，C核对删后不可读；无法证明最新状态则拒绝开放 |
| API/Job状态可用 | RTO≤4小时，自事故确认/停服起，含人工响应、隔离恢复、对账和检查；非长期服务承诺 | B执行、C留证、A放行、D核用户状态；GPU重算/重建积压另报，不偷换为服务就绪 |
| 索引/Redis | 可重建，不承诺恢复原缓存；重建仅使用仍有权且未删除的获准版本 | B/C核发布代与权限，不因缓存恢复扩大数据可读范围 |

备份候选为南京 COS 的独立私有备份桶/前缀、独立受限身份及加密密钥管理，故障域独立于主机磁盘/数据卷；
不能仅在 postgres-data 同盘存 dump。对象独立备份、版本保留、防误删能力和权限必须实查，不推定已配置。
备份上传角色不持全库/全桶删除权限，恢复角色单独授权；密钥可恢复性也需演练。
保留期限、对象历史版本与备份到期受 Q02/Q03/Q09 审批，不在本卡自动批准永久保留或新增真实资料副本。
桶配置、实际操作者姓名、费用及保留期未定，真实资料试点仍阻塞；上述目标仅供 A 审核，不宣称已实现。

最新删除台账必须包含可重放条目而不只是一个整数。删除先在在线API阻断并写Outbox，随后可靠复制独立台账；
仅登记请求的202不等于清理/持久复制完成。外部副本尚未确认时，返回pending，不把删除报告为全部成功。
独立副本不可达、复制存在未决缺口或最新head无法核验时，恢复环境保持关闭；不能把旧备份中自带的水位当最新。

恢复顺序：A宣布停服/写入冻结 → B隔离恢复DB/Temporal及对象清单 → 从独立台账取得可核验最新head和连续条目 →
补齐删除/访问阻断并验证私有内容不可读 → 核对在途Job、admission、未知费用/执行（不自动重做） →
C验证对象/索引/权限和恢复点数据缺口、记录实测RPO/RTO → A批准开放，D核用户状态。
台账缺条目、密钥/对象不可用或恢复目标未达时，不开真实资料路径；限制范围或继续停服由A明确决定。
