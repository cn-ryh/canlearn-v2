# ADR-0002：仓库与部署拓扑

- 状态：已接受
- 决策日期：2026-09-30
- 适用范围：CanLearn MVP 及首个稳定候选版本

## 决策

1. 使用单一 Git monorepo，不把 Next.js、Node.js、Python 和基础设施拆成多个仓库。
2. 仓库内按可部署单元分区：`apps/web`、`apps/api`、`apps/workflow`，MinerU 作为外部独立微服务接入。
3. 使用 `pnpm workspace` 管理 TypeScript 项目，使用 `uv` 独立管理 Python 工作流；两种生态通过根目录脚本和 CI 统一检查。
4. RESTful API 的 OpenAPI 文件集中存放于 `contracts/openapi`，跨服务异步消息另行维护版本化事件 Schema。
5. MVP 使用单地域部署，不建设跨地域主动-主动架构。生产 PostgreSQL、Redis 等有状态服务优先使用同地域多可用区托管能力。
6. Web、API、工作流和 MinerU 保持独立构建与部署能力，仓库合并不等于运行时合并。

## 理由

- 四人团队需要原子化修改前端、API、工作流和契约，单仓库能降低跨仓版本协调与评审成本。
- TypeScript 和 Python 仍保留各自锁文件、工具链和部署单元，不强行统一依赖管理。
- 当前产品尚未验证跨地域流量和容灾成本，提前建设多地域写入会显著增加一致性、运维与测试复杂度。

## 重新评估条件

出现以下情况之一时重新评估拆仓或多地域部署：

- 独立团队拥有明确服务边界和发布节奏；
- 仓库体积或 CI 时间持续影响交付；
- 存在必须隔离的权限、合规或供应链边界；
- 已验证的用户分布、RTO/RPO 或数据驻留要求无法由单地域多可用区满足；
- MinerU 或 GPU 工作负载需要独立基础设施团队维护。
